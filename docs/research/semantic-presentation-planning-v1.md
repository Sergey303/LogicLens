# LogicLens: semantic evidence and deterministic presentation planning

- Status: proposed research gate
- Scope: Search/UI research only
- Does not change: active epoch, transactional runtime, UI Document v0, React renderer

## 1. Decision to test, not yet adopt

LogicLens should not ask an LLM to generate arbitrary UI code or make an opaque final component choice.

The research hypothesis is narrower:

> Can an LLM extract checkable semantic claims from unfamiliar RDF/Prolog data, with explicit evidence and alternatives, so that a deterministic planner can produce a more useful presentation than the generic fallback without losing facts, provenance, reproducibility, or the ability to reject a rich view?

This is not yet an architectural decision. The proposed semantic and presentation layers should enter the stable architecture only after an oracle-controlled experiment proves that they add value.

## 2. Critical conclusions

### 2.1. Semantic interpretation and presentation planning should be separated

The separation is correct because the two stages fail differently:

- semantic interpretation may misunderstand a predicate or entity group;
- deterministic feature extraction may compute the wrong shape;
- the planner may choose the wrong component despite correct inputs;
- UI Document compilation may lose or misrepresent facts;
- React may render a valid document incorrectly.

A single LLM-generated UI Document hides these failure classes inside one artifact and makes diagnosis weak.

### 2.2. LogicLens already contains much of the required boundary

The current architecture already provides:

- canonical `fact/4`, `fact_origin/2`, and `origin/2` data;
- deterministic FactId and explicit provenance;
- a generic representation for unknown predicates and types;
- a closed UI Document vocabulary;
- server-side UI validation and fail-closed fallback;
- a domain-neutral React renderer;
- isolated Search artifacts;
- a Builder promotion boundary;
- an implementation precedent where Qwen selects public FactIds and trusted code renders candidate files deterministically.

The missing part is not another renderer. It is a frozen, replayable contract between semantic claims, deterministic dataset measurements, presentation candidates, and the final UI decision.

### 2.3. The proposed “semantic roles” should not be one flat list

A flat list such as `title`, `time`, `measurement`, `editable`, and `technical metadata` mixes several unrelated dimensions.

Use typed facets instead:

1. **Display role** — how an element identifies or describes an entity:
   - `identifier`
   - `display_label`
   - `description`

2. **Value role** — what kind of value it appears to express:
   - `time_value`
   - `measurement`
   - `category`
   - `status`
   - `relation`
   - `long_text`

3. **Policy role** — how the system should treat it operationally:
   - `technical_metadata`
   - `provenance_metadata`

`editable` must not be an LLM semantic role. Editability is derived from the canonical source (`base` versus `derived`) and trusted server policy.

### 2.4. Presentation Evidence Graph should not become a second ontology

Counts, coverage ratios, graph size, common predicates, literal types, and component availability are measurements, not semantic claims. They should be generated by trusted code and stored in a dataset profile.

The minimum useful separation is therefore:

```text
Canonical Assertion Graph
        ↓
Semantic Claim Record
        ↓
Deterministic Dataset Profile
        ↓
Presentation Decision Record
        ↓
UI Document
        ↓
React
```

The records may be serialized as Prolog facts, JSON, or both, but their responsibilities must remain separate.

## 3. Minimal Semantic IR v1

The first version should store claims, alternatives, evidence, and producer identity. It should not contain UI components, utility scores, or probabilities.

```prolog
semantic_claim(
    ClaimId,
    DataElement,
    Facet,
    Role
).

semantic_claim_status(
    ClaimId,
    Status
).

semantic_claim_evidence(
    ClaimId,
    EvidenceId
).

semantic_evidence(
    EvidenceId,
    Evidence
).

semantic_claim_alternative(
    ClaimId,
    AlternativeClaimId
).

semantic_claim_producer(
    ClaimId,
    Producer
).
```

Allowed statuses for v1:

```text
supported
possible
rejected
unknown
```

Example:

```prolog
semantic_claim(
    claim_created_event_time,
    predicate('fog:created'),
    value_role,
    time_value
).

semantic_claim_status(
    claim_created_event_time,
    possible
).

semantic_claim_evidence(
    claim_created_event_time,
    evidence_created_datatype
).

semantic_evidence(
    evidence_created_datatype,
    datatype('xsd:dateTime')
).

semantic_claim_evidence(
    claim_created_event_time,
    evidence_created_label
).

semantic_evidence(
    evidence_created_label,
    ontology_label("дата создания")
).

semantic_claim(
    claim_created_publication_date,
    predicate('fog:created'),
    value_role,
    publication_time
).

semantic_claim_status(
    claim_created_publication_date,
    possible
).

semantic_claim_alternative(
    claim_created_event_time,
    claim_created_publication_date
).
```

### 3.1. Evidence rules

Evidence must be inspectable and bounded. It may reference:

- canonical FactIds;
- ontology labels and definitions;
- literal datatype;
- neighboring predicates and entity types;
- explicit user-task wording;
- deterministic measurements from the dataset profile.

A natural-language explanation is allowed only as supplementary evidence. It cannot replace machine-checkable references.

### 3.2. Producer provenance

Every claim must record how it was produced:

```prolog
semantic_claim_producer(
    claim_created_event_time,
    llm(
        provider(ollama),
        model('qwen2.5-coder:7b'),
        prompt_hash('sha256:...'),
        evidence_bundle_hash('sha256:...')
    )
).
```

Deterministic claims use a rule or analyzer version instead:

```prolog
semantic_claim_producer(
    claim_name_label,
    analyzer(label_heuristics_v1)
).
```

The model score, when available, may be preserved as diagnostic metadata, but it is not a probability and must not decide applicability.

## 4. Deterministic Dataset Profile v1

Trusted code computes structural and coverage facts from the canonical graph plus accepted semantic claims.

```prolog
dataset_profile(ContextId, ProfileVersion).

profile_measure(
    ContextId,
    Measure
).
```

Example:

```prolog
profile_measure(context_17, entity_count(18)).
profile_measure(context_17, repeated_record_shape(true)).
profile_measure(context_17, common_attribute_count(5)).
profile_measure(context_17, missing_value_ratio(ratio(1, 18))).
profile_measure(context_17, literal_datatype_count('xsd:dateTime', 17)).
profile_measure(context_17, technical_fact_count(46)).
profile_measure(context_17, result_fact_count(211)).
profile_measure(context_17, allowed_component(table, true)).
```

The analyzer, not the LLM, computes:

- entity and fact counts;
- common and optional predicates;
- missingness;
- datatype distributions;
- graph size and depth;
- repeated-record shape;
- candidate row and column coverage;
- exact fact coverage of a proposed view;
- component availability and hard limits.

## 5. Minimal Presentation IR v1

Presentation IR should record the user goal, candidates, their exact inputs, hard constraints, coverage, rejection reasons, fallback, and final selection.

```prolog
presentation_context(
    ContextId,
    Goal
).

presentation_candidate(
    CandidateId,
    ContextId,
    Component
).

candidate_input(
    CandidateId,
    Input
).

candidate_constraint(
    CandidateId,
    Constraint,
    Result
).

candidate_coverage(
    CandidateId,
    Coverage
).

candidate_rejection(
    CandidateId,
    Reason
).

candidate_fallback(
    CandidateId,
    Fallback
).

presentation_decision(
    ContextId,
    Decision
).
```

Example:

```prolog
presentation_context(
    context_17,
    compare_revisions
).

presentation_candidate(
    candidate_table_17,
    context_17,
    comparison_table
).

candidate_input(
    candidate_table_17,
    entities([revision_a, revision_b, revision_c])
).

candidate_input(
    candidate_table_17,
    dimensions([
        'fog:validFrom',
        'fog:material',
        'fog:status'
    ])
).

candidate_constraint(
    candidate_table_17,
    repeated_records_required,
    passed
).

candidate_constraint(
    candidate_table_17,
    minimum_shared_dimensions(2),
    passed
).

candidate_constraint(
    candidate_table_17,
    maximum_columns(12),
    passed
).

candidate_coverage(
    candidate_table_17,
    base_fact_ids([fact_1, fact_2, fact_3, fact_4])
).

candidate_fallback(
    candidate_table_17,
    generic_property_sections
).

presentation_decision(
    context_17,
    selected(candidate_table_17)
).
```

A rejected candidate remains in the record:

```prolog
candidate_constraint(
    candidate_timeline_17,
    unambiguous_time_axis,
    failed
).

candidate_rejection(
    candidate_timeline_17,
    ambiguous_time_semantics
).
```

## 6. Hard constraints before any ranking

A rich candidate is ineligible when any of the following is true:

- the component is absent from the versioned UI contract;
- the required dataset shape is absent;
- a required semantic claim is only `possible` where the contract requires `supported`;
- selected evidence references a missing FactId;
- candidate cells contain invented values;
- base and derived values are mixed incorrectly;
- an editable flag contradicts trusted source policy;
- row, column, component, nesting, or byte limits are exceeded;
- mandatory facts are not covered by either the rich view or an inspectable fallback;
- no generic fallback is attached;
- the candidate cannot explain its rejection and coverage.

No fuzzy score, utility function, or LLM confidence may override a failed hard constraint.

## 7. One primary experiment

### 7.1. Component under test: `ComparisonTable`

The first rich component should be a table, not Timeline, Tree, or Graph.

Reasons:

- repeated records and shared dimensions are measurable deterministically;
- a table has a small, testable data contract;
- comparison tasks have objective completion time and error metrics;
- the renderer does not need domain ontology knowledge;
- Table introduces less navigation and layout confounding than Tree or Graph;
- Timeline depends too strongly on already-correct temporal semantics and would mix the semantic experiment with a more specialized visualization experiment.

This does not mean Table should be added immediately. It becomes eligible only after two gates pass.

### 7.2. Gate A: semantic claims without rich UI

Freeze a benchmark of predicates and entity groups with:

- clear labels;
- opaque or renamed predicates;
- misleading labels;
- mixed datatypes;
- ambiguous time-like fields;
- technical metadata;
- missing values;
- relations that look structurally similar but have different meaning.

Compare:

1. deterministic label/datatype heuristic;
2. LLM semantic claims with evidence;
3. oracle semantic claims.

No UI choice is made in Gate A.

### 7.3. Gate B: planner on oracle inputs

Run the deterministic planner using only oracle semantic claims and trusted dataset profiles.

If the planner cannot reliably decide when a table is useful and when it must fall back, the rich UI direction stops here. LLM integration is not the cause of the failure and should not be added.

### 7.4. End-to-end experiment

Use task families such as:

- compare document or entity revisions;
- find which objects differ by status, material, or category;
- identify missing values across repeated records;
- inspect a repeated structure where technical fields must not become primary columns;
- negative cases where records are structurally repeated but semantically incomparable;
- negative cases where the generic fallback is already sufficient.

Each case includes:

- canonical facts and origins;
- task text;
- oracle semantic claims;
- oracle dataset profile;
- allowed UI components;
- expected acceptable candidate set;
- expected rejection reasons;
- target user questions and answer key.

## 8. Control modes

The first benchmark should compare:

1. **Generic fallback** — existing property sections only.
2. **Deterministic heuristic + planner** — no LLM; labels, datatypes, and graph structure only.
3. **LLM direct component choice** — records only the component selection and explanation.
4. **LLM direct UI Document** — isolated experimental control; schema validation remains mandatory and output never becomes trusted runtime code.
5. **LLM semantic claims + deterministic planner** — proposed mode.
6. **Oracle semantic claims + deterministic planner** — planner upper bound.
7. **LLM semantic claims + expert component choice** — diagnostic mode to isolate planner error.

Not every mode needs to enter the user study. Modes 3, 4, and 7 are primarily diagnostic controls.

## 9. UI Document v0 versus rich components

UI Document v0 is sufficient for:

- Gate A semantic evaluation;
- storing explanations and diagnostics;
- focused property sections;
- generic fallback;
- provenance inspection;
- verifying that semantic claims do not cause fact loss.

Before adding Table, compare two presentations using the same accepted semantic claims:

1. focused UI Document v0 sections;
2. the proposed ComparisonTable.

If focused v0 sections provide the same task benefit, Table should not be added. A new component is justified only by measured incremental value over both generic fallback and focused v0 composition.

## 10. Minimal table contract for a later UI Document version

A future table contract should be domain-neutral and closed:

```text
ComparisonTable
  id
  title
  rowKeyColumn
  columns[]
  rows[]
  diagnostics[]
```

Each column contains only:

```text
id
label
valueKind
semanticClaimIds[]
```

Each cell contains only a trusted UI value with its complete base or derived source.

React must not receive:

- RDF predicate interpretation rules;
- ontology class names as control logic;
- arbitrary formatter code;
- arbitrary props;
- LLM explanations used as rendering instructions.

React renders rows, columns, cells, sorting, and filtering according to the component contract. The planner decides which entities and dimensions enter the table.

## 11. Provenance requirements

### 11.1. Semantic claim provenance

For every claim preserve:

- claim ID;
- data element reference;
- facet and role;
- status;
- alternatives;
- supporting FactIds and ontology evidence;
- producer kind;
- analyzer/model version;
- prompt hash when applicable;
- evidence bundle hash;
- timestamp and run ID.

### 11.2. Presentation decision provenance

For every decision preserve:

- context and user goal;
- dataset profile version and hash;
- accepted semantic claim IDs;
- candidate component IDs;
- planner version;
- rule IDs that evaluated each constraint;
- exact pass/fail result for every hard constraint;
- selected entity and dimension IDs;
- exact covered FactIds;
- rejected candidates and reasons;
- fallback identity;
- compiled UI Document hash.

This provenance must make the final choice reproducible without another LLM call.

## 12. Correct promotion unit from Search to Builder

The promotion unit should be a **view profile**, not an isolated Prolog rule, a loose set of semantic roles, or a copied Search UI Document.

A promoted view profile packages:

- task family;
- applicability rules;
- required semantic facets and statuses;
- deterministic feature requirements;
- component contract version;
- projection and coverage rules;
- fallback;
- rejection explanations;
- regression cases;
- user-study evidence.

Semantic roles remain shared vocabulary. Individual rules may implement parts of a profile, but the profile is the unit whose usefulness and safety were demonstrated end to end.

## 13. Fuzzy values, utility, and probability

They are not required in v1.

### Probability

Use probability only after a semantic-role model has a held-out calibration set. An uncalibrated LLM score remains `model_score`, not probability.

### Utility

Use utility only after user studies provide empirical task metrics. Keep dimensions separate:

- task completion;
- information coverage;
- error rate;
- interaction cost;
- visual density;
- implementation cost.

Do not collapse them into one score until a documented policy explains the weights.

### Fuzzy membership

Use fuzzy membership only for gradual layout properties such as density or compactness. It must not determine semantic correctness or override component applicability.

## 14. Metrics

### 14.1. Safety and completeness

- valid UI Document rate;
- missing or invented FactId references;
- base/derived correctness;
- editability correctness;
- unknown component/prop count;
- mandatory fact coverage;
- fallback availability;
- deterministic replay success.

Required safety target: zero invented facts, zero invalid evidence references, zero editable derived values, and a valid fallback for every run.

### 14.2. Semantic quality

- macro-F1 by facet and role;
- top-k alternative recall;
- ambiguity detection precision/recall;
- false-supported rate;
- robustness to predicate renaming and label paraphrase;
- evidence validity rate.

### 14.3. Planner quality

- agreement with the expert acceptable set;
- false-rich-view rate on negative cases;
- unjustified fallback rate on positive cases;
- exact rejection-reason accuracy;
- selected FactId coverage;
- stability under fact permutation and irrelevant technical additions.

### 14.4. User task utility

- task completion time;
- answer error rate;
- ability to locate source evidence;
- ability to detect conflict and missing data;
- perceived overload;
- trust calibration rather than raw liking.

Visual preference alone is not a success metric.

### 14.5. Cost

- LLM latency and token count;
- planner latency;
- UI Document size;
- number of semantic claims requested;
- cache hit rate for reusable interpretations.

## 15. Error isolation benchmark

Every case must support replay from each frozen boundary:

```text
canonical facts
  -> semantic claims
  -> dataset profile
  -> presentation decision
  -> UI Document
  -> renderer snapshot
```

Required replay modes:

1. LLM claims + trusted profile + planner;
2. oracle claims + trusted profile + planner;
3. oracle claims + oracle profile + planner;
4. oracle presentation decision + UI compiler;
5. golden UI Document + React renderer.

This distinguishes:

- interpretation error;
- feature computation error;
- planner error;
- UI Document compilation/validation error;
- React rendering error.

## 16. Provisional go/stop criteria

The thresholds below are research gates, not product SLAs.

### Continue to rich UI only when

- LLM semantic claims outperform the deterministic heuristic by at least 10 percentage points macro-F1 on the opaque-predicate holdout;
- evidence validity is at least 99% and false-supported claims remain below 5%;
- the oracle planner improves median task completion time by at least 15% over generic fallback on applicable comparison cases without increasing answer errors;
- the oracle planner rejects at least 95% of negative rich-view cases;
- end-to-end LLM + planner retains at least 70% of the oracle planner gain;
- every run preserves complete source provenance and generic fallback;
- planner output is invariant under fact order and irrelevant technical facts.

### Simplify the direction when

- deterministic heuristics are within 5 percentage points of the LLM on semantic quality;
- focused UI Document v0 sections perform as well as ComparisonTable;
- most useful features are already derivable from datatypes, graph shape, and ontology labels;
- LLM claims require frequent expert repair;
- rich views improve preference but not task completion or error rate.

### Stop the direction when

- the oracle planner does not beat generic fallback;
- the oracle planner cannot reliably reject semantically misleading tables;
- fact coverage or provenance becomes weaker than the generic view;
- UI plans are unstable under harmless input transformations;
- the end-to-end system produces a material false-confidence increase;
- the cost and latency exceed the measured user benefit.

## 17. Recommended implementation order

1. Freeze benchmark cases and gold semantic claims.
2. Implement only the Semantic IR serializer and validator.
3. Add deterministic dataset-profile extraction.
4. Implement planner rules with generic/focused-v0 output only.
5. Run the oracle planner gate.
6. Run LLM semantic-claim evaluation.
7. Compare focused UI Document v0 with a static table prototype.
8. Add a versioned ComparisonTable contract only after the previous gates pass.
9. Run the controlled user study.
10. Consider Builder promotion of a complete view profile.

## 18. Resulting architecture principle

> The LLM may propose semantic claims and evidence. Trusted analyzers compute dataset shape. A deterministic planner applies hard constraints, records rejected alternatives, selects a presentation, and compiles a versioned UI Document. React only renders that validated document.

The generic view remains the control, fallback, completeness oracle, and lower bound throughout the experiment.
